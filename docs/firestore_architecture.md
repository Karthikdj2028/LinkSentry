# LinkSentry Cloud Firestore Architecture & Scan History Foundation

## 1. Firestore Data Hierarchy

LinkSentry uses a per-user subcollection hierarchy to enforce strict data isolation, simplify security rule evaluation, and support unified multi-platform synchronization across Web and mobile (Android).

```text
users/ (Collection)
  └── {userId}/ (Document: User profile / settings)
        └── scans/ (Subcollection)
              └── {scanId}/ (Document: Individual scan assessment record)
```

### Full Document Path
```text
users/{userId}/scans/{scanId}
```

---

## 2. Scan Document Schema

Each scan record created by the detection pipeline adheres to the following standardized schema:

| Field Name | Type | Description | Example Value |
| :--- | :--- | :--- | :--- |
| `userId` | `string` | Authenticated user's Firebase UID | `"u4xK9pLm1Z9q7Vb3..."` |
| `type` | `string` | Scanning vector category (`"url"`, `"qr"`, `"message"`) | `"url"` |
| `input` | `string` | Original input provided for inspection | `"https://example.com/login"` |
| `url` | `string` | Evaluated URL target or extracted link | `"https://example.com/login"` |
| `domain` | `string` | Parsed hostname / FQDN | `"example.com"` |
| `verdict` | `string` | Security threat verdict (`"safe"`, `"suspicious"`, `"phishing"`, `"invalid"`) | `"safe"` |
| `riskScore` | `number` | Calculated risk index from 0 to 100 | `15` |
| `confidence` | `number` | Detection engine confidence level (0.00 – 1.00) | `0.70` |
| `indicators` | `string[]` | Heuristic and rule-based threat signals | `["Connection does not use HTTPS"]` |
| `engine` | `string` | Threat engine identifier | `"temporary-rule-based-detector"` |
| `createdAt` | `timestamp` | Server-generated timestamp | `FieldValue.serverTimestamp()` |

## 3. Why `userId` is the Authenticated Firebase UID

1. **Cryptographically Verified Identity**: The Firebase UID (`request.auth.uid`) is generated by Google's authentication service upon registration and signed in JSON Web Tokens (JWT). It cannot be spoofed by client manipulation.
2. **Immutable Reference**: Unlike email addresses or usernames (which can be edited, deleted, or transferred), the Firebase UID is unique and permanent for the lifetime of the analyst account.
3. **Defense-in-Depth in Security Rules**: Having the document path include `{userId}` and verifying `request.resource.data.userId == request.auth.uid` guarantees that every database write is validated at the document boundary.
4. **No Sensitive Auth Secrets in Firestore**: Passwords, hashes, and session refresh tokens are managed exclusively by Firebase Authentication and are never stored in Cloud Firestore.

## 4. Security Rules Architecture (`firestore.rules`)

The security policy rejects all unauthenticated operations and enforces strict per-user authorization boundaries:

```javascript
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {

    // Default deny-all
    match /{document=**} {
      allow read, write: if false;
    }

    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;

      match /scans/{scanId} {
        // Read & Delete: Only the owner matching this subcollection path can access
        allow read, delete: if request.auth != null && request.auth.uid == userId;

        // Create & Update: Owner must match path AND internal userId payload
        allow create, update: if request.auth != null 
          && request.auth.uid == userId
          && request.resource.data.userId == request.auth.uid;
      }
    }
  }
}
```

### Access Matrix

| Request Scenario | Authenticated? | User Matching | Result | Reason |
| :--- | :--- | :--- | :--- | :--- |
| Unauthenticated Read/Write | ❌ No (`null`) | N/A | **REJECTED** | `request.auth != null` fails |
| User A reads User A scans | ✅ Yes | `userId == request.auth.uid` | **ALLOWED** | Owner matches path |
| User A reads User B scans | ✅ Yes | `userId != request.auth.uid` | **REJECTED** | Cross-tenant access blocked |
| User A writes scan under User B path | ✅ Yes | `userId != request.auth.uid` | **REJECTED** | Path and UID mismatch |
| User A writes scan with User B UID inside data | ✅ Yes | `userId == request.auth.uid` | **REJECTED** | `request.resource.data.userId == request.auth.uid` check fails |

## 5. Cross-Platform Shared History (Web + Future Android App)

Both the **LinkSentry React Web Application** and the **LinkSentry Android Mobile App** will connect to the **same Firebase Project**:

```text
 ┌───────────────────────────────┐        ┌───────────────────────────────┐
 │   LinkSentry React 19 Web     │        │   LinkSentry Android Native   │
 │      (Web Firebase SDK)       │        │     (Firebase Android SDK)    │
 └──────────────┬────────────────┘        └───────────────┬───────────────┘
                │                                         │
                │  Sign In (Email / Password)             │  Sign In (Email / Password)
                │  Firebase UID: "u4xK9p..."              │  Firebase UID: "u4xK9p..."
                ▼                                         ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │                      Firebase Authentication                           │
 └──────────────────────────────────┬─────────────────────────────────────┘
                                    │
                                    │ Evaluates security rules:
                                    │ request.auth.uid == userId
                                    ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │                          Cloud Firestore                               │
 │                                                                        │
 │   users/u4xK9p.../scans/                                               │
 │     ├── scan_001 (Saved from Web Scanner)                             │
 │     └── scan_002 (Saved from Mobile App Scanner)                       │
 └────────────────────────────────────────────────────────────────────────┘
```

1. When an analyst logs in on the website, they authenticate against Firebase Auth and receive UID `u4xK9p...`.
2. When the same analyst logs in on their Android device, Firebase Auth returns the identical UID `u4xK9p...`.
3. When querying `users/{userId}/scans`, both clients receive the unified audit trail in real time.
4. If a scan is performed on the Android app, it appears in the Web history table, and vice-versa.
